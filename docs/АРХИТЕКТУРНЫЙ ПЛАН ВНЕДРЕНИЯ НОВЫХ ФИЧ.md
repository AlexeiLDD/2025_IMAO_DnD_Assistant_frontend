# Архитектурный план: Fog of War / Vision / Pathing

> Encounterium BattleMap — SVG + d3.zoom + Redux
> Canonical reference for Fog, Lighting/Vision, and Pathing subsystems.

---

## A) Рекомендованный подход

**Grid-based** модель для всех трёх подсистем. Карта уже дискретна (`cols=26, rows=18, cellSize=50` в `BattleMap.tsx:24-26`), и D&D 5e оперирует 5-футовой сеткой. Вектор-полигоны дороги в diff/sync и сложны для SVG-масок; растр не имеет смысла при 468 ячейках. Grid даёт:
- O(1) доступ по координатам, тривиальный diff (список `[row, col, value]`)
- SVG-рендер через **один `<path>`** на слой (склейка rect-команд в `d`), т.е. 1 DOM-элемент вместо 468
- Прямое соответствие существующему `cells: boolean[][]` (`BattleMap.tsx:21`)
- Простой PATCH-протокол, совместимый с текущим `encounter_patch` паттерном (`encounterTrackerSessionProvider.tsx:186-228`)

Три подсистемы **независимы по данным, но связаны по вычислениям:**
- **Fog** = history маска (explored/unexplored) + computed visibility. Не блокирует свет.
- **Vision/Lighting** = источники света + raycast через **occlusion** (terrain/walls), не через fog.
- **Pathing** = статичная разметка terrain. `blocked` terrain используется как **occlusion** для line-of-sight.

> **Ключевое правило:** Fog — UI/информационный слой (что игрок уже видел). LoS/свет блокируется occlusion (terrain `blocked` / walls), а fog — только маска отображения для рендера.

## A.1) Locked Decisions

> These decisions are **final**. Do not revisit without explicit team approval.

### D1. Auto-reveal fog: mover-authoritative

When a token moves, the **mover's client** computes newly visible cells and sends `fog_history_patch`. Other clients **apply the patch only** — they do not recompute fog history independently.

**Pipeline:**
```
mover client: onTokenMoveCommit (dragEnd)
  → recomputeVisibility(movedToken, visionSources, occlusionGrid)
  → newlyVisible = cells where visibility=true AND history=0
  → dispatch(applyFogHistoryPatch(newlyVisible))
  → send fog_history_patch via WS

other clients: receive fog_history_patch
  → apply patch to Redux (anti-echo skips mover)
  → recompute DerivedFogValue for render
```

**DM override:** DM can manually reveal/hide any cell via `fog-brush` tool at any time. Both auto-reveal and DM brush use the same `applyFogHistoryPatch` action and the same `fog_history_patch` WS message.

**Why mover-authoritative, not independent computation:**
- Inputs can temporarily diverge between clients (e.g. `occlusionGrid` arriving via `pathing_patch` at different times). Mover-authoritative guarantees a single source of truth for each reveal event.
- Simpler to debug: one client sends, others apply. No "two clients computed different results" edge case.
- Consistent with the existing `encounter_patch` pattern where the acting client sends and others apply.

### D2. Visibility aggregation rule

**Visibility for a player = union of visibility of ALL tokens controlled by that player.**

A cell is "visible" for player P if ANY token owned by P can see that cell (raycast from token position through occlusion grid, within light/darkvision radius).

**"Controlled by":** determined by `Participant.ownerId` field (maps to `PlayerId`).
> **TODO:** `ownerId` does not exist on the current `Participant` type. Must be added when implementing per-player fog. Until then, `party` mode treats all tokens as collectively owned.

### D3. Per-player fog privacy

| Backend mode | `perPlayer` fog privacy | Status |
|-------------|------------------------|--------|
| Mode A (relay-only) | **NOT private.** All clients receive all `fog_history_patch` messages regardless of `scope`. Functional but players can see each other's fog history in devtools. | Current backend. |
| Mode B (server-filtered fan-out) | **Private.** Server routes `scope="player"` patches only to `playerId` + DM. | Requires backend changes. See `docs/BACKEND_API_BACKLOG.md`. |

For MVP (Iterations 1–2): use `mode: 'party'` only. Per-player fog is Iteration 3.

## B) Stored vs Computed — Data Model

### Что хранится (Redux + sync) vs что вычисляется (ephemeral)

| Data | Storage | Sync | Owner | Notes |
|------|---------|------|-------|-------|
| `FogHistoryGrid` (`0\|1` per cell) | Redux `fog.history*` | `fog_history_patch` | DM (manual brush) + system (auto-reveal on move) | Per-party or per-player |
| `LightSource[]` | Redux `vision.sources` | `vision_patch` | DM | Point entities with radius |
| `TerrainGrid` (`0\|1\|2` per cell) | Redux `pathing.grid` | `pathing_patch` | DM | Also serves as **occlusion** for LoS |
| `OcclusionGrid` | **Decision point:** derive from `TerrainGrid` (blocked=opaque) or store separately | — or `occlusion_patch` | DM | Separate grid needed only if walls ≠ blocked terrain |
| `VisibilityMask` (`boolean[][]`) | **Computed** — `useMemo`/`useRef` | Never synced | Each client locally | `= raycast(sources, occlusion, tokenPosition)` |
| `LightLevelGrid` (`0\|1\|2`) | **Computed** — `useMemo`/`useRef` | Never synced | Each client locally | `0=dark, 1=dim, 2=bright` from sources + occlusion |
| `DerivedFogValue` (`0\|1\|2`) | **Computed** for render | Never synced | Each client locally | `= visible ? 2 : explored ? 1 : 0` |

### State Schema (TypeScript)

```typescript
// ─── Fog of War ───

/** What is STORED: exploration history. 0 = never seen, 1 = seen at least once */
type FogHistoryValue = 0 | 1;
type FogHistoryGrid = FogHistoryValue[][]; // [row][col]

/** What is COMPUTED for render: 0 = unexplored (black), 1 = explored (dim), 2 = currently visible */
type DerivedFogValue = 0 | 1 | 2;
// derived = isVisible(row,col) ? 2 : history[row][col] === 1 ? 1 : 0

type PlayerId = string; // UUID or stable session id

type FogState = {
  enabled: boolean;
  /**
   * 'party' — one shared history grid for all players (simpler, MVP).
   * 'perPlayer' — each player has own history (requires server fan-out for privacy).
   */
  mode: 'party' | 'perPlayer';
  /** Used when mode='party'. Shared exploration history. */
  historyParty?: FogHistoryGrid;
  /** Used when mode='perPlayer'. Keyed by player ID. */
  historyByPlayer?: Record<PlayerId, FogHistoryGrid>;
};

// ─── Lighting / Vision ───

type LightSource = {
  id: UUID;
  cellX: number;
  cellY: number;
  /** Bright light radius, in cells (= ft / 5) */
  brightRadius: number;
  /** Dim light radius, in cells */
  dimRadius: number;
  color: string; // hex, default '#fff5c0'
  /** Attach to token — source moves with creature on drag */
  attachedTo?: UUID;
};

type VisionState = {
  sources: LightSource[];
  darkvisionRadius: number; // global default, in cells
  // VisibilityMask and LightLevelGrid are COMPUTED, not stored here
};

// ─── Pathing / Terrain ───

/** 0 = normal, 1 = difficult terrain (×2 movement cost), 2 = blocked (impassable + occlusion) */
type TerrainValue = 0 | 1 | 2;
type TerrainGrid = TerrainValue[][]; // [row][col]

type PathingState = {
  grid: TerrainGrid;
  enabled: boolean;
};

// ─── Integration into existing slice ───
// Added to encounter.slice.ts alongside participants
type EncounterState = {
  // ... existing fields ...
  fog: FogState;
  vision: VisionState;
  pathing: PathingState;
};
```

### Per-player fog: privacy model

| Mode | Data on client | Sync model | Privacy |
|------|---------------|------------|---------|
| `party` | Single `historyParty` grid, same for everyone | Broadcast fog_history_patch to all | No privacy needed — all see same fog |
| `perPlayer` | Each client gets only their own `historyByPlayer[myId]` | **Server must filter:** fan-out only relevant player's history | Requires backend change (mode B below) |

DM always sees `DerivedFogValue` with `opacity=0.3` (sees through fog). Players see `opacity=1.0` for unexplored.

## E) Auto-reveal Pipeline

> **Locked decision D1 applies.** Auto-reveal is mover-authoritative. See section A.1.

When a token moves, the **mover's client** computes newly visible cells and sends them as a patch. Other clients apply the patch without recomputing.

```
MOVER CLIENT:
  onTokenMoveCommit (dragEnd dispatch)
    → recomputeVisibility(movedToken, visionSources, occlusionGrid)
    → newlyVisible = cells where visibility=true AND history=0
    → dispatch(encounterActions.applyFogHistoryPatch(newlyVisible.map(c => [c.row, c.col, 1])))
    → send fog_history_patch { scope, playerId, cells } via WS

OTHER CLIENTS:
  receive fog_history_patch
    → anti-echo check (origin === CLIENT_ID → skip)
    → dispatch(encounterActions.applyFogHistoryPatch(patch.cells))
    → recompute DerivedFogValue for render (local useMemo)
```

**Invariants:**
- Two sources of fog history mutation: (1) auto-reveal on token move (mover-authoritative), (2) DM manual brush. Both use the same `applyFogHistoryPatch` action and `fog_history_patch` WS message.
- Auto-reveal targets the **moving token's owner** (in `perPlayer` mode) or `historyParty` (in `party` mode).
- Visibility for a player = **union of all tokens controlled by that player** (locked decision D2).
- Other clients never independently compute fog history changes from remote token moves — they only apply the received patch.

## F) Patch Formats

> **Canonical sync invariants (anti-echo, initial FULL gate, diff base, fallback rules) are defined in `docs/NETWORK_SYNC_CONTRACT.md`.** This section defines only payload shapes. Any new patch type must be registered in the NETWORK_SYNC_CONTRACT "Patch Domains" table BEFORE implementation.

### `fog_history_patch` (canonical name)

```json
{
  "type": "fog_history_patch",
  "data": {
    "origin": "client_1706..._a3f",
    "scope": "party",
    "playerId": null,
    "cells": [
      [3, 5, 1],
      [3, 6, 1],
      [4, 5, 1],
      [4, 6, 1]
    ]
  }
}
```

- `cells` — array of `[row, col, newHistoryValue]`. Values: `0` (unexplored) or `1` (explored). **Never `2`** — visible is computed, not synced.
- `scope`: `"party"` — applies to shared history; `"player"` — applies to specific player's history.
- `playerId`: required when `scope="player"`, null otherwise.
- Max patch size: 468 triples (full map), typical brush stroke: 5–20.

**Privacy note:** In `perPlayer` mode, broadcasting `fog_history_patch` with `scope="player"` to ALL clients leaks that player's fog history to others. This requires server-side fan-out (mode B in Backend section) to send each player's patch only to that player + DM.

### `vision_patch` (light sources)

```json
{
  "type": "vision_patch",
  "data": {
    "origin": "client_...",
    "op": "upsert",
    "sources": [
      {
        "id": "light_abc123",
        "cellX": 10,
        "cellY": 7,
        "brightRadius": 4,
        "dimRadius": 8,
        "color": "#fff5c0",
        "attachedTo": "creature_xyz"
      }
    ]
  }
}
```

`op`: `"upsert"` | `"remove"` (remove → only `id` needed).

### `pathing_patch`

```json
{
  "type": "pathing_patch",
  "data": {
    "origin": "client_...",
    "cells": [
      [7, 12, 2],
      [7, 13, 2],
      [8, 12, 1]
    ]
  }
}
```

Format identical to fog_history_patch (but `cells` values are `TerrainValue`: 0/1/2).

### SessionMessage type union

```typescript
// entities/session/model/types.ts
type: 'error' | 'participantsInfo' | 'battleInfo'
    | 'encounter_patch'
    | 'fog_history_patch'   // canonical (was fog_patch)

```

All inbound handlers follow the pattern from `encounterTrackerSessionProvider.tsx:186-228`:
anti-echo via `origin`, `isApplyingRemoteRef` flag, diff base update. See `docs/NETWORK_SYNC_CONTRACT.md`.

## H) Performance Notes

| Technique | Where | Why |
|-----------|-------|-----|
| One `<path>` per layer | `FogOverlay`, `PathingOverlay`, `VisionOverlay` | 1 DOM element instead of 468 `<rect>` |
| `useMemo` on `d` string | Every overlay | Rebuild path string only when grid changes |
| Batch stroke → one dispatch | `useFogBrushTool` | Don't dispatch on every `pointerMove`; collect array |
| `requestAnimationFrame` throttle on preview | Brush tools | Preview rect updates at max 60 fps |
| `computeVisionGrid` in `useRef` + deps | Vision | Don't recompute raycast on every render |
| Fog `<path>` with `pointer-events="none"` | `FogOverlay` | Fog doesn't intercept clicks on tokens underneath (for DM) |
| Derived fog = `useMemo(history, visibility)` | `FogOverlay` consumer | Never store derived values in Redux; recompute from history + visibility |

## I) Backend Assumptions / Future Changes

### Mode A: Relay-only (MVP)

Server acts as a dumb relay: broadcasts every WS message to all clients in the session.

- **Pros:** No backend changes needed. Works for `party` fog mode.
- **Cons:** No per-player privacy. All clients receive all fog history. `perPlayer` mode leaks data.
- **Use for:** Iterations 1–2, Iteration 3 without per-player fog.

### Mode B: Server-filtered fan-out

Server inspects `fog_history_patch` messages. If `scope="player"`, sends the patch only to:
- The specified `playerId`'s client
- The DM client(s)

All other message types (`vision_patch`, `pathing_patch`, `encounter_patch`) remain broadcast.

- **Pros:** Proper per-player fog privacy.
- **Cons:** Requires backend to know player→connection mapping and to parse message types.
- **Use for:** Iteration 3 `perPlayer` mode.
- **Fallback:** If backend changes are delayed, `perPlayer` mode can be feature-flagged off. The architecture supports both modes without frontend changes — only the `scope` field in the patch determines behavior.

### Decision points for backend team

1. Does the server need to persist fog/vision/pathing state, or is it client-authoritative with the DM's client as source of truth?
2. Should the initial `battleInfo` snapshot include per-player fog, or should each player request their own history via a separate endpoint?
3. Is `perPlayer` fog needed for v1, or is `party` mode sufficient?

See `docs/BACKEND_API_BACKLOG.md` for the full endpoint/event backlog.
